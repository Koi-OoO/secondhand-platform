# 订单核心流程检查与阅读路线

## 调用链

`OrderController → OrderService → OrderServiceImpl → OrderMapper / ProductMapper`

Controller 从当前登录态获取用户ID，Service 判断买家/卖家身份与订单状态，不信任客户端指定的操作人。

## 下单

1. 校验数量、地点与商品ID，获取商品维度 Redis 锁。
2. 查询商品，校验在售、非本人商品、库存充足、面交地点未变。
3. 拒绝同一买家对同一商品已有未完成订单的再次下单。
4. 保存商品标题、图片、单价和地点快照，新订单为待接单；按数量扣库存。
5. 删除详情缓存、发布商品变化并通知卖家。

订单和库存写入位于同一个数据库事务，运行时异常会触发回滚。快照用于保留交易当时的约定，不随商品后来修改而变化。

## 取消与拒单

1. 使用 `SELECT ... FOR UPDATE` 锁定订单，再校验操作人和状态。
2. 仅待接单或待面交允许取消/拒单，记录取消类型、时间和原因。
3. 获取商品 Redis 锁，按订单数量恢复库存；原为售罄且恢复后有库存时转为在售，下架商品不会自动上架。
4. 删除缓存、发布商品变化并通知对方。通知实时推送在事务提交后执行。

订单行锁在事务结束时释放，后到的取消/拒单请求应读到已取消状态，从而避免再次回补。单元测试只能验证判断分支，不能证明真实并发数据库行为。

## 本轮修复

回补拿不到锁时原先仍继续修改库存；等待锁中断时原先吞掉异常，可能只提交订单取消。现在这两种情况均抛出运行时异常，由 Spring 回滚当前事务；批量拒单遇到此类异常时整个批次回滚，而不是返回部分成功。

## 尚未解决的并发边界

- 下单和回补均在方法内部释放 Redis 锁，而 Spring 事务在方法返回后才提交；后一个请求可能在提交前拿到锁并读取旧库存。
- Redis 锁固定租期10秒，耗时超过租期后不能继续依靠这把锁保证互斥。
- 商品上下架使用不同前缀的 Redis 锁，不能与订单商品锁形成统一保护；多个入口读改写同一商品需一并设计数据库层的库存保护。
- 本轮未修改锁顺序或库存SQL，未运行真实并发联调。下一步应统一评估商品写入口，补数据库行锁或条件原子更新，并验证真实事务下的并发下单、回补和回滚。

## 面试需要讲清的点

- 为什么订单和库存必须在同一个事务？返回错误对象与抛出异常对事务有什么区别？
- 订单行锁如何拦截重复取消？它与 Redis 商品锁分别保护什么？
- 为什么保存商品快照、为什么通知要提交后推送？
- 为什么仅使用 Redis 锁并不能在当前实现中证明不会超卖？
