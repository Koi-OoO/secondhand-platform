# 查询缓存对照测试

仅比较查询缓存。Redis 继续运行：登录会话、验证码、热词、浏览量和分布式锁依然需要它。

## 开关

在 IDEA 的 Java Run/Debug Configuration 中添加或修改 Environment variables，保留其他变量。修改后重新启动后端。

| 场景 | CATEGORY_CACHE_ENABLED | PRODUCT_DETAIL_CACHE_ENABLED |
| --- | --- | --- |
| 分类查询：无缓存组 | false | true |
| 分类查询：缓存组 | true | true |
| 商品详情：无缓存组 | true | false |
| 商品详情：缓存组 | true | true |

两项默认都是 true；测试结束后恢复 true。分类开关由 Spring Cache 注解读取，详情开关由 ProductServiceImpl 读取。详情关闭时仍使用原数据库加载方法查询商品及图片，AI 详情读取也遵守同一开关。商品修改、下单等操作的缓存删除继续保留。

## 验证与采集

1. 每次只测一个接口。分类使用 GET /category/list；商品详情使用 GET /product/detail/{id}，选择同一个有效商品 ID。例如本机后端地址为 http://localhost:8080/product/detail/40（40 需替换为真实商品 ID）。
2. 先发送少量请求，检查 HTTP 状态、业务 code=200、分类或商品字段及图片列表。临时观察 SQL，关闭缓存时重复请求应持续查询数据库，开启且命中时不应重复加载商品/分类数据。正式压测时关闭大量 SQL 输出。
3. 固定数据库、数据规模、JVM/连接池配置、机器与 JMeter 参数，使用 Run 模式而非 Debug。每组重启后先预热 30～60 秒，预热不计入正式结果。
4. 初始用 10 并发、10 秒 ramp-up、持续 120 秒，逐步增加到 30、50 并发。每组至少重复 3 次，交替测试开关状态。GUI 用于调试，正式测试用 JMeter 非 GUI 模式，保存每条请求的 JTL 原始数据和测试计划。
5. 对比相同并发下的吞吐量、平均响应时间、P95、错误率，配合数据库查询次数和 Redis 命中情况。未测到系统瓶颈时不能把吞吐量称为“最大 QPS”。

商品详情正常访问仍会写浏览统计，关闭缓存不代表接口完全不访问 Redis。统计会定时写回数据库，两组应保持一致并记录测试时长。此方案测的是已有有效商品的正常读取；不存在商品、防穿透、缓存过期重建和写入一致性应另设测试，不与稳定命中结果混合。

分类注解代理测试使用内存 CacheManager，商品详情开关测试使用模拟依赖，验证分支与业务行为；它们不代替真实 MySQL/Redis 的压测。真实对照结果才能写进简历，注明机器与并发条件。
